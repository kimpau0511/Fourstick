상태: 초안 · 작성: <이름> · 관련 요구사항: <SFR-00N 등, `docs/PRD.md`> · 관련 ADR: <없음 / ADR-00N>

## 1. 무엇을 (What)
입력 → 출력, 관측 가능한 동작. 무엇이 들어가고 무엇이 나오는가.

## 2. 왜 (Why) · 성공 기준
누가 어떤 문제 때문에 쓰는가. 성공했는지 **숫자나 실행 명령으로** 말할 수 있어야 한다.
- 예: "그거 옮겨줘" 발화 20건 중 확인 카드 없이 실행되는 작업 0건

## 3. 제약 (Constraints)
지켜야 할 한계 — 응답 시간, 하위 호환, 기존 계약(`core/`), `AGENTS.md`의 안전 불변식 중 해당하는 것.

## 4. 경계 (Boundaries)
이 스펙에서 **손대지 않는 것**과 그것을 다루는 곳. 빠지면 AI가 멋대로 범위를 넓힌다.
- 예: G1 경로는 건드리지 않는다 → `specs/g1-xxx.md`에서 다룸

## 5. 엣지 케이스
빈 입력 · 타임아웃 · 부분 실패 · 설정 누락 · 관측 오래됨 · STOP 중 요청 · 모델 서버 없음 …
각각 어떤 이유 코드(`core/reason_codes.py`)로 끝나는가.

## 6. 인터페이스 시그니처
산문이 아니라 시그니처로 적는다. 박아두면 추측의 여지가 사라진다.
```python
def example(material_id: str, *, session_id: str) -> ExampleResult: ...
```

## 준비 체크리스트 (전부 체크돼야 구현 시작)
- [ ] 모든 요구에 구체적인 완료 기준(수용 기준)이 있다
- [ ] 엣지 케이스가 나열돼 있고 각각의 결과(이유 코드)가 정해져 있다
- [ ] 제약이 명시돼 있다
- [ ] 경계(손대지 않는 것)가 정의돼 있다
- [ ] 인터페이스 시그니처가 적혀 있다

## 구현 단계

단계 설계 원칙:
1. **범위 최소** — 한 단계는 한 계층·한 모듈만. 여러 모듈을 동시에 고쳐야 하면 단계를 쪼갠다.
2. **자기 완결** — 각 단계는 새 세션에서 실행된다고 가정한다. "앞에서 논의한 대로" 같은 참조 금지, 필요한 정보는 단계 안에 적는다.
3. **먼저 읽을 파일 명시** — 코드를 읽고 맥락을 파악한 뒤 작업하게 한다.
4. **시그니처 수준 지시** — 인터페이스만 주고 내부 구현은 맡긴다. 단, 안전 규칙은 반드시 명시한다.
5. **수용 기준은 실행 가능한 명령** — "~가 동작해야 한다"가 아니라 테스트 명령.
   외부 프로세스가 필요한 검증은 "사람 확인"으로 따로 적는다.
6. **주의사항은 구체적으로** — "조심해라"가 아니라 "X를 하지 마라. 이유: Y".

단계가 3개 이상이면 단계마다 새 세션에서 시작한다(`docs/SDD.md` 구현 규칙).
