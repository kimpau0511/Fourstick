## 한 줄 정의

작업자의 한국어 음성·자연어 명령을 사람이 읽을 수 있는 **JSON Task Plan**으로 바꾸고,
형식 → 의미·안전 규칙 → 기하·경로 검사를 모두 통과한 계획만 로봇에 전달하는 **로봇 작업지시 미들웨어**.

## 문제와 가설

- 산업용 로봇의 작업 설정 변경은 티칭펜던트·제조사 환경·좌표 지식을 요구해 비전문가에게 어렵다.
  단 이것은 **검증 전 가설**이다 — 재설정 빈도·소요시간·담당 주체·외부 SI 의존은 협력기업 인터뷰로 확인한다.
- LLM 출력은 확률적이라 "자연어를 이해했다"와 "안전하게 실행할 수 있다"는 다르다
  → **계획 생성과 실행 허가를 분리**한다(`docs/ADR.md` ADR-001).

## 사용자

- 1차: 다품종 소량생산 제조 협력기업의 현장 작업자(로봇 전문가 아님).
- 2차: 대학·직업훈련·스마트팩토리 교육기관(판정·이유 코드·계획 검증 실습).

## 범위와 전제

- 목적은 **가상환경에서 음성 → 계획 → 검사 → 판정 → 가상 실행의 전체 흐름이 작동함을 구조적으로 검증**하는 것.
  실물 로봇 구동과 기능 안전 인증은 검증 대상이 아니다.
- STOP은 소프트웨어 수준의 실행 취소 경로이며 **하드웨어 비상정지·기능 안전 장치를 대체하지 않는다.**
- LLM은 정해진 원자 스킬만 조합한다(기획서 기준 home·move·pick·place·stop). 관절각·모터 명령은 생성하지 않는다.
- 판정은 PASS(실행 가능)·BLOCK(차단)·ASK(추가 확인)로 나누고 모든 판정에 이유 코드를 남긴다.

## 요구사항 (29건)

상세 세부 내용은 원본 기획서 "요구사항 정의서". "관련 코드"는 모듈 docstring으로 확인한 것만 적었다.
빈칸은 **구현 여부·위치 미확인** — 추측하지 말고 코드를 확인하거나 사람에게 묻는다.

## 동기화 규칙

- 요구사항·범위·목표가 바뀌는 작업은 **같은 작업 안에서** 이 파일을 고친다. 기능 스펙(`specs/`)은 관련 요구사항 ID를 적는다.
- 기획서가 바뀌면 이 파일의 해당 부분을 갱신하고 위 "원본"의 기준 날짜를 바꾼다.
- 코드가 기획서와 달라지면 "기획서와 다른 점"에 추가한다. 리뷰 때 PRD 반영 여부를 확인한다.
