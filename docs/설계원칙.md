# forstick2 설계 원칙

시스템이 **어떻게 동작해야 하는가**를 정한 규칙이다. 코드를 어떻게 쓰는가(코딩 규칙)와
AI와 어떻게 일하는가(협업 절차)는 `CODE_RULES.md`에 있다.

- 이 문서의 원칙은 새로 정한 것이 아니라 **이미 코드에 있는 설계**를 옮겨 적은 것이다.
  각 절에 근거 파일을 적었다. 근거 파일은 모두 2026-09-17 초기 반입 때 들어왔다.
- 2026-10-02 `CODE_RULES.md`에서 분리했다(원래 1·3·4·5·9번). `CODE_RULES.md`의
  절 번호는 그대로 두고 이 문서를 가리키게 했다.
- 원래 설계 문서(`md/개발플랜.md`, `md/웹UI_구조.md`, `md/저장소_설계.md`)는
  `.gitignore`로 저장소에 없다. 코드 주석이 그 문서를 가리키면 원문은 팀원 로컬에 있다.

## 1. 데이터 접근 — 브라우저·라우트는 DB에 직접 접근하지 않는다

브라우저와 라우트는 DB에 직접 접근하지 않는다. 저장은 항상 `storage/repository.py`의
인터페이스를 거친다.

근거와 이유(`server/api.py`, `storage/repository.py`, `storage/sqlite/repository.py`,
`storage/records.py` 모듈 설명):

- **검사를 한 곳에 모은다.** 멱등성·유일성(같은 `request_id`에 다른 내용 거부, 같은
  요청의 동시 실행 거부)과 append-only(상태 전이·검증 결과·관측·실행 결과는 고치지 않고
  추가만)를 저장소가 강제한다. 다른 경로로 DB에 쓰면 이 검사를 건너뛴다.
- **소유 관계를 확인한다.** API는 모든 조회를 명시적 식별자(`session_id`·`request_id`·
  `plan_id`·`plan_hash`·`approval_id`·`execution_id`)로 하고, 그 기록이 이 세션의 것인지
  저장소에서 확인한다. 서버는 "현재 계획"을 추정하지 않는다.
- **DB를 바꿀 수 있게 한다.** SQL·연결·트랜잭션은 `storage/sqlite/` 안에만 둔다.
  PostgreSQL 구현을 더해도 core 계약과 API 스키마는 바뀌지 않는다.
- **트랜잭션 경계를 지킨다.** 쓰기는 `BEGIN IMMEDIATE`~`COMMIT` 구간을 직접 열고 락으로
  직렬화한다. 웹 서버가 여러 스레드에서 같은 DB를 쓰기 때문이다.

세션은 **인증이 아니다**(`server/api.py`). 세션 id를 아는 클라이언트는 그 세션 자료에
접근할 수 있다. 인증은 개발플랜이 정한 단계에서 붙인다.

## 2. 화면은 서버 값을 그대로 보여준다

관제 대시보드(`dashboard2/`)는 판정·요약·자리를 서버 값 그대로 보여준다. 화면이 만들지
않는다.

## 3. 값이 없으면 추정하지 않고 차단한다

수치·정책 값에 **기본값을 두지 않는다.** 호출자가 명시하지 않으면 값을 추정하지 말고
`PolicyError`/해당 `ReasonCode`로 차단한다(`core/policy.py`).

## 4. "확인 안 됨"은 "통과"가 아니다 — 이 프로젝트의 가장 중요한 원칙

`validation/execution_permit.py`에 명시된 원칙이고, 코드 전반에 일관되게 적용된다.

- 관측값이 없거나(`None`), 오래됐거나, 무효(`valid=False`)면 **그 자체로 거부 사유**다.
  "일단 통과시키고 나중에 확인"은 없다.
- Safety 판정이 `ALLOW`가 아니면 실행 불가 — **`ASK`(정보 부족)도 실행 허가로 치지
  않는다.** `BLOCK`과 동급으로 막는다.
- 여러 조건이 동시에 실패할 수 있으면 **사유를 전부 모아서 반환**한다. 하나 고치고
  재시도했더니 다른 이유로 또 막히는 상황을 피하기 위해서다.
- 확인되지 않은 값을 사용자 자기신고나 체크박스로 메워서 통과시키지 않는다.

새 검증 로직을 짤 때 이 네 가지를 기본 태도로 삼는다.

## 5. 실행 직전 재검증 — 계획 만들 때 검사한 걸 실행 때 또 본다

`validation/execution_permit.py`, `core/stop_contract.py` 공통 원칙.

- **생성 시점에 검증했다고 실행 시점에 안 보지 않는다.** plan hash, TTL, robot
  준비상태, Profile/Policy/환경 snapshot 버전을 실행 요청이 들어올 때마다 다시 대조한다.
- 안전 관련 상태 전환(정지 래치, goal 추적 등)은 **하나의 임계구역(락) 안에서**
  pending 등록/해제까지 같이 처리한다 — "확인하고 → 등록"을 분리하면 그 사이에
  경쟁조건이 생긴다(`core/stop_contract.py`의 R1/R2가 이 이유로 존재).
- ACK/성공 응답만으로 상태를 확정하지 않는다. 가능하면 실측(관절 정지 등)까지 같이
  본다(R8/R9).

## 6. 시뮬레이션 통과는 실기 준비 완료가 아니다

`simulation_e2e`와 `real_hardware_ready`를 끝까지 다른 값으로 다룬다. **시뮬레이션에서
통과했다고 실기 준비 완료로 자동 승격하지 않는다**(`validation/hardware_readiness.py`:
Gazebo 이송 시연은 실기 준비 판정의 입력이 아니다).
