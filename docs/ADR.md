# 결정 기록 (ADR)

**구조를 바꾸기 전에 읽는다.** 에이전트가 이유를 모르면 멀쩡한 결정을 "개선"하려 든다.
각 항목의 근거는 괄호 안 파일에 있다. 이유를 코드에서 확인할 수 없으면 지어내지 않고 "팀 확인 필요"로 둔다 —
새 결정을 내리면 같은 형식으로 추가하고, 결정을 뒤집으면 지우지 말고 `대체됨`으로 표시한다.

형식: **결정** / **이유** / **포기한 것**(있을 때). 이유 끝의 `파일:줄`은 그 문장이 적힌 주석 위치다.

---

### ADR-001 LLM은 계획만, 실행 권한은 규칙 검증기
- **결정**: 모델 출력은 계획 초안일 뿐이고, 실행 여부는 규칙 기반 검증기와 실행 직전 재검증(Permit)이 정한다.
- **이유**: 요구정의서의 이중 안전 구조. 모델은 카탈로그·안전 규칙을 모두 지키면서도 사용자가 요청하지 않은 계획을 만들 수 있다 — 5-02 실측에서 그런 계획 5건이 실행 허가까지 통과했다. (`validation/execution_permit.py:3-6`, `planning/pipeline.py:12-15`)

### ADR-002 모호하면 계획 대신 되묻는다
- **결정**: 모델이 "확인 필요"라고 하면 계획을 만들지 않고 질문을 전달한다. 모델이 참조한 리소스도 카탈로그와 다시 대조한다.
- **이유**: 모호한 요청에 그럴듯한 계획을 만드는 것보다 되묻는 게 안전하다. 입력에 허용 목록을 줬다고 출력이 그 안에 있다고 가정할 수 없다. (`planning/pipeline.py`)
- **포기한 것**: 한 번에 실행되는 편의성.

### ADR-003 정보 부족은 통과가 아니다
- **결정**: 안전 규칙 판정은 PASS/BLOCK/INSUFFICIENT_DATA/NOT_APPLICABLE 4단계이며, INSUFFICIENT_DATA는 ASK로 집계되고 실행 허가로 치지 않는다. 값이 없으면 추정·기본값으로 채우지 않는다.
- **이유**: "확인 불가"가 성공으로 바뀌면 안 된다. (`validation/safety_validator.py`, `core/reason_codes.py`)

### ADR-004 STOP은 계획·LLM을 거치지 않는다
- **결정**: 실제 정지는 `/v1/stop` → 어댑터 STOP 계약(`core/stop_contract.py`)으로만 한다. 계획·검증·허가를 거치지 않는다. 결과는 `exec.stopped`(정지 확인)와 `exec.stop_unconfirmed`(미확인)로 구분하며, 요청 접수를 정지 확인으로 치지 않는다.
- 발화에 정지 키워드가 있으면 계획기(`planning/pipeline.py`)가 모델을 건너뛰고 stop 계획을 만들지만, 이것은 **요청의 표현이지 실행 경로가 아니다** — stop 단독 계획은 안전 검증(home 종료 요구)을 통과하지 못하는 게 맞다.
- **이유**: 정지는 모델 응답을 기다릴 일이 아니고, 계획 검증·허가를 기다리면 정지가 늦어진다. STT 경로와 텍스트 경로에 같은 규칙을 둔다. (`planning/pipeline.py:115-120`, `server/api.py`)

### ADR-005 실행 직전에 전부 다시 판정한다
- **결정**: 계획 생성 시점이 아니라 실행 요청 시점에 관측값으로 다시 판정하고, 실패 사유는 하나가 아니라 전부 모아 돌려준다.
- **이유**: 상태는 시간이 지나면 바뀐다. 사유를 하나씩 주면 고치고 재시도할 때마다 다른 이유로 또 막힌다. 신선도 임계값은 코드 상수가 아니라 정책에서 온다. (`validation/execution_permit.py`)

### ADR-006 서버는 '현재 계획'을 추정하지 않는다
- **결정**: 모든 작업은 session_id·request_id·plan_id·plan_hash·approval_id·execution_id로 조회하고 소유 관계를 저장소에서 확인한다. 전역 상태를 두지 않는다.
- **이유**: 새 요청이 다른 세션의 계획을 덮어쓰지 않게 한다. 대화 맥락도 브라우저 세션별로 분리한다. (`server/api.py:8-11`, `README.md:143`)

### ADR-007 모호한 자재 발화는 좁은 분류기 + 확인 카드
- **결정**: 시연 경로에서 Qwen은 계획을 만들지 않고 `{intent, material_id, confidence}` JSON만 낸다. 서버가 재검증해도 바로 실행하지 않고 확인 카드를 띄운다. 만료(60초)·취소·상태 변경·낮은 confidence·JSON 오류는 모두 작업 0건이다. 모델 서버가 없으면 ASK로 끝난다.
- **이유**: 추측해서 실행하지 않는다. (`server/sim_demo_intent.py`, `server/sim_demo_confirm.py`, `README.md`)

### ADR-008 시연 작업은 검증된 스크립트를 별도 프로세스로 실행
- **결정**: 웹 시연 버튼은 서버 안에서 로봇을 직접 움직이지 않고 `scripts/demo_workcell_pick_place.sh`를 별도 프로세스로 돌린다. 한 번에 하나만 돌고, 정지는 정지 요청 파일로 전달하며 프로세스를 강제로 죽이지 않는다.
- **이유**: 스크립트가 진입 조건·재검증·STOP·체크포인트·래치를 이미 지킨다. 강제로 죽이면 궤적이 남는다. (`server/sim_demo_jobs.py:3-15`)

### ADR-009 없는 기능을 있는 것처럼 만들지 않는다
- **결정**: LLM 서버·STT 모델·실제 로봇 Profile이 없으면 `available=False`·"로봇 미설정"으로 보고한다. Mock 성공 응답으로 대체하지 않는다. 브라우저에 모델 서버 주소·인증값을 내려보내지 않는다.
- **이유**: 코드에는 원칙만 있고 이유는 적혀 있지 않다 — 팀 확인 후 보완. (`server/runtime.py`)

### ADR-010 이유 코드는 한 곳에서만 정의
- **결정**: 모든 실패·거부 사유는 `core/reason_codes.py`의 `<category>.<reason>` 코드로 표현한다.
- **이유**: UI와 감사 로그가 분류별로 묶어 보여준다. 다른 계층에서 문자열을 직접 만들어 쓰지 않는다. (`core/reason_codes.py`)

### ADR-011 인증은 아직 없다 — 지금은 localhost 전제
- **결정**: 세션 id는 인증이 아니라 작업 묶음 식별자다. 인증은 개발플랜이 정한 단계에서 붙인다.
- **이유**: 코드 주석은 "현재 구성은 localhost 전용이며 사용자 계정이 없다"를 전제로 한다. (`server/api.py:20-24`)
- **주의**: 이 전제는 이미 깨질 수 있다 — README가 인증 없는 LAN 실행(`run_web_lan.sh`, 0.0.0.0:8094)과 TLS(`run_web_tls.sh`)를 안내한다. 외부 노출·실기 연결·데모 외부 접속 전에는 인증을 먼저 붙인다.
